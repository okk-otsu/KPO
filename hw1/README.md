# ВышКат — учёт парка

Консольное приложение на Go для домашнего задания №1 по КПО. Реализованы приёмка транспорта после техосмотра, учёт вещей, отчёт по количеству и энергии, подбор транспорта для новичков и общий инвентарь.

## Запуск

Нужен Go 1.22 или новее. Сторонних зависимостей нет.

Если установлен `make`, из папки `hw1` доступны команды:

```bash
make          # сборка в bin/vyshkat
make run      # интерактивный запуск
make demo     # демонстрация
make check    # тесты, race, vet и сборка
make coverage # отчёт о покрытии
make clean    # удаление бинарного файла и coverage.out
```

Отдельные проверки: `make test`, `make race`, `make vet`.

```bash
go run .
```

Автоматическая демонстрация с отображением вводимых значений:

```bash
go run . --demo
```

Справка по параметрам запуска:

```bash
go run . --help
```

Неизвестные флаги и лишние позиционные аргументы приводят к завершению с ошибкой.

Сборка и запуск отдельного исполняемого файла:

```bash
mkdir -p bin
go build -o bin/vyshkat .
./bin/vyshkat
```

Меню: `1` — транспорт, `2` — вещь, `3` — отчёт, `4` — транспорт для новичков, `5` — инвентарь, `0` — выход. Названия могут содержать пробелы. Для энергии подходят и `2.5`, и `2,5`. На вопрос об исправности нужно ответить `да` или `нет` без учёта регистра. После некорректного значения или отказа в добавлении операция отменяется, приложение возвращается в меню. Конец ввода завершает приложение без добавления недозаполненного объекта. Ошибка чтения завершает приложение с сообщением об ошибке.

Данные хранятся в памяти одного запуска. Сохранение на диск, аренда и авторизация в условии не требуются. Приложение однопоточное.

## Правила и решения

- У всех объектов на балансе есть непустые название и инвентарный номер. Номер — строка, поэтому возможны `S-001` и ведущие нули. Краевые пробелы удаляются; регистр значим. Номера уникальны среди транспорта и вещей одновременно.
- `Scooter` — электросамокат, `ElectricBike` — электровелосипед, `Bicycle` — обычный велосипед. Последний не реализует `EnergyConsumer`, поскольку не потребляет электричество.
- Вещи представлены `Helmet` и `ChargingStation`. Шлем не потребляет электричество, зарядная станция потребляет. Они не являются транспортом и не попадают в выдачу новичкам.
- Простота транспорта — целое число от 1 до 10. Для новичков подходит принятый транспорт с простотой **от 6 включительно**.
- Энергия измеряется в кВт·ч за сутки и должна быть конечным неотрицательным числом. Отрицательные числа, `NaN` и бесконечность отклоняются.
- Точные критерии техосмотра в условии не заданы. Принято учебное правило: `TechnicalServiceCenter` допускает исправную технику и отклоняет неисправную с указанием причины. Признак исправности вводит оператор как результат диагностики. Расход энергии сам по себе не является причиной отказа.
- Вся постановка на баланс проходит через `Fleet.Add`. Сначала проверяются объект, номер и характеристики. Затем для объекта, реализующего `Transport`, вызывается сервис техосмотра; добавить транспорт «как вещь» в обход проверки нельзя. При занятом номере техосмотр не вызывается. Ошибка или отказ не меняют парк. Номер отклонённой техники можно использовать повторно после ремонта.
- Отчёт выводит общее количество, количество транспорта и вещей, энергию транспорта и энергию всего баланса. Так расход зарядной станции не теряется и при этом не смешивается с расходом собственно флота в отдельной строке.
- Инвентарь и список для новичков отсортированы лексикографически по номеру для воспроизводимого вывода.

## Устройство проекта

| Файл | Ответственность |
| --- | --- |
| [main.go](main.go) | Аргументы запуска, создание контейнера, запуск приложения |
| [internal/fleet/model.go](internal/fleet/model.go) | Интерфейсы, виды транспорта и вещей, конструкторы с проверками |
| [internal/fleet/service.go](internal/fleet/service.go) | Техосмотр, постановка на баланс, отчёты и подбор для новичков |
| [internal/console/app.go](internal/console/app.go) | Меню, ввод, сообщения об ошибках |
| [internal/console/demo.go](internal/console/demo.go) | Сценарий демонстрации через настоящее меню |
| [internal/di/container.go](internal/di/container.go) | Создание и связывание зависимостей одного приложения |

Один путь выполнения: пользователь вводит самокат → `NewScooter` проверяет его поля → `Fleet.Add` проверяет номер → `ServiceCenter.Inspect` принимает решение → при успехе объект попадает в карту инвентаря → отчёт учитывает его энергию.

В Go вместо наследования классов используется композиция: самокат содержит общие части `vehicle` и `energyUsage`, велосипед — только `vehicle`, зарядная станция — `item` и `energyUsage`. Встраивание продвигает их методы. Интерфейсы реализуются неявно. Поля закрыты, конструкторы возвращают значения; штатные объекты нельзя изменить после добавления через публичный API. Внешние реализации интерфейсов должны сохранять номер и характеристики после приёмки. `Fleet.Add` дополнительно проверяет объекты на границе, в том числе нулевые значения и интерфейсы с nil-указателем.

Для небольшого приложения модель и бизнес-операции оставлены в одном пакете `fleet`. Нет базы данных, репозиториев, универсальных фабрик и отдельного интерфейса для каждого типа.

## SOLID и обязательные вопросы

### Какой принцип наиболее явно применён?

**DIP — инверсия зависимостей.** `Fleet` зависит от интерфейса `ServiceCenter`, а не создаёт `TechnicalServiceCenter` самостоятельно. Зависимость передаётся в `fleet.New`. В тестах вместо настоящего осмотра используется `inspectionStub`. Консольный ввод и вывод также передаются как `io.Reader` и `io.Writer`.

### Где применены остальные принципы?

- **SRP:** модели проверяют собственные характеристики; техосмотр принимает решение о допуске; `Fleet` управляет учётом; `console.App` общается с пользователем; `di.Container` связывает объекты. Изменение текста меню не требует менять расчёт энергии.
- **OCP:** `Fleet` обрабатывает интерфейсы `InventoryItem`, `Transport` и `EnergyConsumer`, а не переключается по конкретным моделям. Новый транспорт участвует в осмотре, отчёте и подборе без изменений `Fleet`. Это проверяет `TestExtensionAndInvalidObjects` с типом, объявленным только в тесте.
- **LSP:** все виды транспорта предоставляют номер, название, простоту и исправность и могут использоваться там, где нужен `Transport`. Обычный велосипед не вынужден притворяться потребителем энергии. Отказ в приёмке — нормальное решение сервиса, а не нарушение контракта транспорта.
- **ISP:** инвентаризируемый объект не обязан потреблять энергию или иметь простоту для новичка. Поэтому шлему не нужны фиктивные методы `DailyEnergy` и `BeginnerEase`.

### Какой принцип сознательно ограничен и почему?

**OCP ограничен на уровне консольного меню.** В `App.addTransport` и `App.addThing` есть `switch` для создания известных видов объектов. Добавление типа потребует добавить пункт меню и вызов конструктора, но не менять учёт и отчёты. Реестр фабрик с динамическими формами для пяти типов усложнил бы домашнее задание без практической пользы. Это осознанный компромисс, а не заявление о полной закрытости всей программы для изменений.

### Как работает DI-контейнер?

`di.Container` — небольшой типизированный контейнер с заранее известными зависимостями. `di.New` создаёт настоящий сервис техосмотра, парк и консольное приложение. `di.NewWithServiceCenter` позволяет передать другую реализацию. Контейнер предоставляет только готовое приложение. Сервис и парк передаются в конструкторы при сборке; заменить их присваиванием полям контейнера нельзя. Разные контейнеры имеют независимое состояние.

Это ручной DI-контейнер без внешней библиотеки и автоматического поиска типов. Приложение и парк не получают контейнер и не ищут в нём зависимости: всё передаётся через конструкторы. Поэтому контейнер не используется как Service Locator. Reflection в `fleet.isNil` служит только для проверки nil внутри интерфейса и не относится к разрешению зависимостей.

### Что изменится при расширении?

- **Новый вид транспорта:** добавить тип, реализующий `Transport`, при необходимости `EnergyConsumer`, его конструктор и пункт меню. Техосмотр по признаку исправности, общий учёт, расчёт энергии и правило новичков продолжат работать. Для более сложной диагностики можно заменить `ServiceCenter` через контейнер.
- **Сотрудник:** создать отдельный тип и отдельный учёт сотрудников. Он не должен реализовывать `InventoryItem`, так как по условию сотрудники не ставятся на баланс. Текущий парк менять не нужно.
- **Склад запчастей:** отдельную инвентаризируемую вещь можно добавить через `InventoryItem`. Для складских остатков с количеством и движением потребуется отдельный сервис склада и его меню; не нужно изображать количество деталей расходом энергии или транспортом. Контейнер свяжет новый сервис с приложением.

### Какие тесты фиксируют решения и как подменяется зависимость?

- `TestInspectionDecisionThroughDI`: `inspectionStub` передаётся в `fleet.New`. Проверяются оба решения сервиса и число вызовов. Даже неисправный самокат принимается при положительном решении заглушки — так тест доказывает, что `Fleet` не дублирует правило настоящего техосмотра.
- `TestContainerInjectsServiceIntoConsole`: отклоняющий сервис передаётся через `di.NewWithServiceCenter`; введённый в консоли исправный велосипед отклоняется, парк остаётся пустым.
- `TestBeginnersBoundary`: значения 1, 5, 6 и 10; в результат попадают только 6 и 10.
- `TestRejectedNumberCanBeRetried`: отказ не меняет энергию и не резервирует номер.
- `TestDuplicateAcrossTypesDoesNotInspectOrReplace`: вещь и транспорт не могут иметь одинаковый номер; исходный объект не заменяется.
- `TestReportAndInventory`: смешанный парк, оба итога энергии, количество, сортировка и независимость возвращаемого среза.
- `TestConstructorsIdentity`, `TestTransportEaseValidation`, `TestEnergyValidation`, `TestExtensionAndInvalidObjects`: ограничения полей, нулевые значения, nil и расширение модели.
- `TestDemo`, `TestInvalidInputAndRecovery`, `TestEOFDuringEveryInputStep`, `TestReadFailure`, `TestDecimalCommaAndCase`: демонстрация, восстановление после ошибок, незавершённый ввод, ошибка чтения, запятая и регистр ответа.
- `TestRun`: обычный запуск, демонстрация, справка, неизвестный флаг и лишний аргумент.

## Проверка

Из папки `hw1`:

```bash
make check
make coverage
make demo
```

`make check` запускает тесты, проверку гонок, `go vet` и сборку. `make coverage` создаёт `coverage.out` и выводит покрытие по функциям.

## Что демонстрирует --demo

1. Отчёт, инвентарь и список новичков пустого парка.
2. Приём исправного самоката с простотой 6 и энергией 2.5.
3. Приём электровелосипеда с простотой 5 и энергией 4.
4. Приём обычного велосипеда с простотой 10.
5. Добавление шлема и зарядной станции с энергией 1.5.
6. Отказ неисправному самокату и отказ при повторном инвентарном номере.
7. Ошибки простоты, энергии, типа объекта и команды с продолжением работы.
8. Итог: **5 объектов, 3 транспорта, 2 вещи; 6.50 кВт·ч/сутки транспорта и 8.00 всего**. Для новичков подходят `B-001` и `S-001`; электровелосипед с простотой 5 не подходит.
9. Общий инвентарь и выход.

Демонстрация прогоняет заранее записанный ввод через настоящее меню, а не печатает заранее подготовленные отчёты.
