# ПОС — преподавательская оценка студентов

Консольное приложение на Go для учёта студентов, критериев и оценок. Позволяет рассчитать итоговый балл и экспортировать результаты в CSV.

Учебный проект по дисциплине «Конструирование программного обеспечения», домашнее задание № 2.

## Запуск

Требуется Go 1.27.3 или новее, согласно `go.mod`.

Из корня проекта:

```sh
go run ./cmd/pos
```

Для сборки и запуска отдельного исполняемого файла на macOS:

```sh
go build -o pos ./cmd/pos
./pos
```

## Работа с приложением

| Команда | Действие |
| --- | --- |
| 1 | Показать студентов и их идентификаторы |
| 2 | Добавить студента: имя и группа |
| 3 | Показать критерии оценивания |
| 4 | Добавить критерий: название, максимальный балл и вес |
| 5 | Выставить или исправить оценку |
| 6 | Показать оценки студента |
| 7 | Отменить оценку |
| 8 | Рассчитать итог студента |
| 9 | Экспортировать итоги всех студентов в новый CSV-файл |
| 10 | Показать текущую успеваемость по выставленным оценкам |
| 0 | Завершить работу |

Идентификаторы студентов создаются автоматически. Для операций с оценками скопируйте идентификатор из списка студентов. Критерий выбирается по названию без учёта регистра.

Повторное выставление оценки тому же студенту по тому же критерию заменяет предыдущий балл. Отмена удаляет оценку.

### Сценарий демонстрации

1. Командой `2` добавьте студента с именем «Студент А» и группой «Группа 1».
2. Командой `4` добавьте критерий «Практика»: максимум `20`, вес `40`.
3. Добавьте критерий «Экзамен»: максимум `10`, вес `60`.
4. Командой `1` получите идентификатор студента.
5. Командой `5` выставьте ему `15` за «Практику» и `8` за «Экзамен».
6. Командой `6` проверьте оценки, командой `8` рассчитайте итог — `8`.
7. Командой `9` экспортируйте результаты, указав новый путь, например `results.csv`.
8. Завершите работу и запустите приложение снова: студенты, критерии и оценки сохранятся.

## Правила оценивания

Приложение работает с одной дисциплиной: список студентов и рубрикатор общие. Отдельная сущность дисциплины не вводится.

- Имя студента, группа и название критерия не могут быть пустыми. Пробелы по краям удаляются.
- Максимальный балл критерия — положительное целое число.
- Вес критерия — целое число от `1` до `100`. Сумма весов не обязана равняться `100`.
- Названия критериев уникальны без учёта регистра; идентификаторы критериев также уникальны.
- Оценка — целое число от `0` до максимума критерия включительно.
- Оценку можно выставить только существующему студенту и только по критерию из рубрикатора.
- Пропущенная или отменённая оценка учитывается при расчёте как `0`; вес критерия остаётся в знаменателе.
- При пустом рубрикаторе расчёт итога возвращает ошибку.

### Формула итога

```text
итог = round(10 × Σ(вес × балл / максимум) / Σ(вес))
```

Результат находится на шкале от `0` до `10`. Округление выполняется до ближайшего целого; половина округляется вверх для неотрицательных значений.

Для примера выше:

```text
10 × (40 × 15/20 + 60 × 8/10) / (40 + 60) = 7,8 → 8
```

Текущая успеваемость (команда `10`) использует ту же формулу, но учитывает в числителе и знаменателе только критерии с выставленными оценками. Выставленный `0` учитывается; пропущенные и отменённые оценки исключаются. Если оценок нет, возвращается ошибка. Например, при двух критериях с равными весами и единственной оценке `8/10` итог равен `4`, а текущая успеваемость — `8`. CSV всегда содержит итог по всем критериям.

Итог не хранится отдельным полем: он вычисляется из текущих оценок и рубрикатора.

## Хранение и экспорт

Студенты, критерии и оценки хранятся в `data.json` в корне проекта — рядом с `go.mod`. В `cmd/pos/main.go` корень определяется по абсолютному пути исходного файла `cmd/pos/main.go`, записанному при сборке, с переходом на два уровня вверх. Папка запуска и расположение исполняемого файла на путь хранилища не влияют.

Собирайте программу без `-trimpath`: этот флаг удаляет необходимый абсолютный путь. Если определить корень невозможно, программа завершится с сообщением об ошибке. После переноса проекта в другую папку пересоберите программу, чтобы она использовала новый корень.

Если файла нет, приложение начинает с пустого состояния и создаёт его при первом успешном изменении данных. Каждое изменение сохраняется автоматически: сначала записывается временный файл в той же папке, затем он переименовывается в файл хранилища. При загрузке данные восстанавливаются через доменные конструкторы с проверкой правил модели. Повреждённый файл приводит к ошибке чтения данных.

Имя файла задано в вызове `jsonrepo.NewRepository` в точке сборки приложения; полный путь собирается через `filepath.Join(projectRoot, "data.json")`. Параметров командной строки для изменения пути сейчас нет.

Экспорт CSV содержит столбцы:

```text
student_id,name,group,final_score
```

Разделитель — запятая, кодировка — UTF-8 с маркером BOM для распознавания кодировки табличными редакторами. Экспорт создаёт только новый файл: существующий файл не перезаписывается. Относительный путь экспорта также отсчитывается от рабочей папки.

## Доменная модель

В основе решения — DDD (предметно-ориентированное проектирование). Единый язык модели: студент, критерий, рубрикатор, оценка и итог.

| Понятие | Тип в коде | Роль |
| --- | --- | --- |
| Студент | `student.Student` | Entity (сущность): определяется устойчивым `StudentID`, содержит имя и группу |
| Критерий | `grading.Criterion` | Сущность с `CriterionID`, названием, максимумом и весом |
| Рубрикатор | `grading.Rubric` | Граница агрегата критериев: контролирует добавление, уникальность и поиск |
| Оценка | `grading.Grade` | Value Object (объект-значение): сочетание идентификаторов студента и критерия с баллом, без собственного идентификатора |
| Расчёт итога | `grading.CalculateFinalScore` | Domain Service (доменный сервис): объединяет правила рубрикатора и оценок |

Поля доменных структур закрыты. Конструкторы проверяют допустимость значений, а рубрикатор возвращает копию среза критериев. Исправление оценки создаёт новое значение `Grade` и заменяет предыдущее.

Проверка существования студента и замена оценки для пары «студент — критерий» выполняются в прикладном слое. Доменный конструктор оценки проверяет принадлежность критерия рубрикатору и диапазон балла.

## Архитектура

Используется облегчённая Clean Architecture (чистая архитектура). Зависимости направлены к домену и прикладным абстракциям.

```text
cmd/pos                         сборка приложения
internal/
  domain/
    student/                    студент и его правила
    grading/                    критерии, рубрикатор, оценки, расчёт итога
  application/                  сценарии и порт хранилища
  adapters/
    console/                    консольный интерфейс
    csvexport/                  запись результатов в CSV
  infrastructure/
    jsonrepo/                   JSON-хранилище и преобразование данных
```

Направления зависимостей:

```text
console → application → domain
csvexport → application → domain
jsonrepo → application → domain
cmd/pos → console, application, jsonrepo
```

Домен не зависит от консоли, файлов и форматов сериализации. Прикладной слой обращается к Repository (репозиторию) через интерфейс `application.Repository` с операциями `Load` и `Save`. JSON-хранилище реализует этот порт. DTO (объекты передачи данных) и преобразование между ними и доменом находятся в `jsonrepo`.

DI (внедрение зависимостей) выполняется вручную через конструкторы в `cmd/pos/main.go`: создаются хранилище, прикладной сервис и консоль. Это composition root (точка сборки приложения).

Ручная сборка зависимостей — осознанный выбор для небольшого приложения и идиоматичный подход в Go. Граф зависимостей явно виден в одной функции, совместимость типов проверяется компилятором, а отдельная библиотека для сборки не требуется. Зависимости передаются через конструкторы, поэтому реализации можно подменять в тестах. Отдельный DI-контейнер не используется: для текущего масштаба проекта ручной сборки достаточно. Это решение является осознанным отступлением от буквального требования задания о DI-контейнере.

## Паттерны и текущие ограничения

- Порождающий паттерн — фабрика: функция `grading.NewGrade` служит единой точкой создания оценки. Она проверяет непустой идентификатор студента, наличие критерия в рубрикаторе и диапазон балла от `0` до максимума критерия. Закрытые поля `Grade` не позволяют внешним пакетам напрямую задать некорректные значения. Фабрика централизует инварианты: консоль и JSON-хранилище используют одинаковые правила создания оценки. Такой вариант соответствует примеру порождающей фабрики из условия ДЗ. В Go он реализован обычной функцией без иерархии классов. Аналогично `NewStudent` и закрытая `newCriterion` проверяют правила создания студентов и критериев.
- Структурный паттерн Facade (фасад) — `application.Service`: предоставляет консоли единую точку доступа к сценариям, скрывает загрузку состояния, проверки связей и сохранение.

- Поведенческий паттерн Strategy (стратегия) — интерфейс `grading.ScoreStrategy` и реализации `FinalScoreStrategy` (все критерии) и `CurrentScoreStrategy` (только выставленные оценки). Решает задачу разных правил для итоговой оценки и текущей успеваемости. Общая проверка оценок, взвешивание и округление вынесены в закрытую функцию домена. Стратегии передаются в `application.NewServiceWithScoreStrategies` в точке сборки; `NewService` использует эти же стратегии по умолчанию. Сервис вызывает расчёт через интерфейс; консоль и JSON-хранилище не знают формул. Экспорт использует итоговую стратегию.
